# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.0.0] - Unreleased

2.0 is a new major line; 1.x lives on the `1.x` branch. [UPGRADE-2.0.md](UPGRADE-2.0.md) walks through every change below that needs one on your side.

### Backward-incompatible changes

- Everything under **Removed**, and the changes listed in [UPGRADE-2.0.md](UPGRADE-2.0.md).
- A name in `extraction.interop` that is no preset is a configuration error that names the preset it most likely means, `laravel-str` giving `illuminate-support`, where it was ignored with a warning: `regex lint --interop` and `regex.json` stop `regex lint` and `regex debug` with exit code 2, the Symfony bundle throws `InvalidConfigurationException`, Laravel's `regex:lint` stops with `Invalid config/php-regex.php`, the PHPStan extension refuses its configuration, where it passed over the name silently, and the language server shows the error and reads as without `regex.json`. An `interop` list made only of unknown names no longer falls back to the native calls only. The language server shows any `regex.json` it cannot read as an error, where it logged a warning. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `Model\DfaState` reads its moves through `transitionFor()`, `rangeCount()` and `ranges()`: the public `$ranges` and `$transitions` arrays are gone. A state holds its ranges as three ints in one list, so the DFA of `/[\pL0-9]*0[0-9]{6}$/um`, about 177,000 ranges, holds 23 MB where it held 59 MB, and peaks at 53 MB where it peaked at 125 MB while it is built. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- A limit of the library is no longer reported as an invalid pattern. `RecursionLimitException` and `ResourceLimitException` extend the new `LimitException`, beside `ParserException` rather than under it, so a `catch (ParserException)` for grammar errors no longer takes them; `validate()` gives them the new `ValidationErrorCategory::Limit` (`limit`), with a hint naming the option to raise, where it said `syntax`; the lint reports such a pattern as a warning, `Not analyzed: …`, and the language server as information (its hover says `Not analyzed`), where both called it an error; `regex validate` prints `NOT ANALYZED` and the option to raise, where it printed `INVALID`; Laravel `regex:explain` and `regex:transpile` say `Pattern not analyzed:`, where they said the pattern was invalid; the PHPStan rule says nothing about such a pattern, where it reported it invalid for the target.
- `regex lint`, Symfony's and Laravel's `regex:lint` and the language server report each `@regex-ignore` or `@regex-ignore-next-line` marker that silences nothing, and `regex lint --baseline` each entry no issue takes any more in a file the run reads or in a file gone from a path it lints, as an error, `regex.ignore.unmatched` (a warning in the editor), on the marker's line or the entry's file and line. An identifier naming a check the run leaves off (`regex.lint.redos` without `--redos`, a lint rule turned off) is passed over; one that names no check the library knows is reported. A run over a part of the project says nothing of the entries of the files it does not read. `--no-report-unmatched-ignores`, `reportUnmatchedIgnores` in `regex.json` and `report_unmatched_ignores` in the bundle and in Laravel's configuration turn the report off. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `@regex-ignore` and `@regex-ignore-next-line` are read where they start a comment, or a line of a doc comment: a marker quoted or met in the middle of a sentence (`// legacy, @regex-ignore`) is prose and silences nothing, where any comment holding the text silenced its line. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `regex lint --baseline` reads a new file format, `{"version": 1, "issues": [...]}`, and matches an issue on its identifier, its file and a hash of its pattern, the line only deciding between equal entries: a pattern that moves down its file or a message reworded in a later release no longer brings a baselined issue back. A 1.x baseline is still read the 1.x way, with a note suggesting to generate it again. A baseline file that is missing, empty or not a baseline, and a baseline that cannot be written, are now a usage error (exit code 2). `--baseline <file>` and `--generate-baseline <file>` now also take their file after a space, as the help said and as `--output` does; either option with no file (nothing after it, an option after it, or an empty `=` value) is a usage error. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- The JSON, Checkstyle and JUnit reports carry each pattern exactly as written, a line break or a control character included; only bytes that are not valid UTF-8 are written `\xHH`, and in Checkstyle and JUnit also the characters XML 1.0 cannot hold: the C0 controls but tab, line feed and carriage return as `\xHH`, U+FFFE and U+FFFF as `\x{FFFE}` and `\x{FFFF}`. They went through the console's escaping, which spelled a newline `\n` and a tab `\t`. The console and GitHub reports show a pattern so that it reads back as the same pattern: the characters that hide or move text (C1 controls, every Unicode format character such as a bidirectional override, a zero-width space, a byte order mark or a tag character, and the line and paragraph separators) are escapes (`\x{202E}` under `/u` or `(*UTF)`, `\xE2\x80\xAE` otherwise), and a pattern under `x` is shown on one line without its `#` comments.
- The PHPStan messages show `<pattern>` as the console does and cut it after 50 characters, never inside a character or an escape: the ReDoS messages, `preg_match() with %s is …` and `Regex pattern can be optimized: "%s"`. A cut used to land inside a multi-byte character and put invalid UTF-8 in PHPStan's output, and a pattern under `x` spread over several lines. The `Consider using:` tip shows the suggested pattern the same way, whole, and the PHP string of a trivial-match message spells those same hidden characters as `\u{…}`. A PHPStan baseline holding such a pattern is generated once more.
- `regex:lint` in Laravel fails (exit code 1) on a file whose validation rules it could not read, where it skipped the file without a word: the file is reported under the new identifier `regex.lint.source.unreadable`.
- `RedosAnalyzer` reports a pattern as not analysed only when the library itself refuses it; any other error, a bug in the confirmation runner included, now surfaces instead of becoming an `Unknown` verdict.
- The library ships as seventeen packages, `php-regex/regex-*`, from the `php-regex/php-regex` repository: `regex-toolkit` holds the `Regex` facade and pulls in every library, `regex-parser` the parser alone, and `regex-phpstan`, `regex-psalm`, `regex-rector`, `regex-phpunit`, `regex-symfony`, `regex-laravel`, `regex-cli` and `regex-language-server` the integrations. `yoeunes/regex-parser` stays on 1.x. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- Every class moved from `RegexParser\` to `PHPRegex\`, under the package it ships in (`Parser`, `Explain`, `Optimizer`, `Generator`, `Automata`, `Redos`, `Transpiler`, `Linter`, `Toolkit`, `Cli`, `LanguageServer`, `PHPStan`, `Symfony`, `Laravel`), and many are renamed for what they are: `RegexParser\Regex` is `PHPRegex\Toolkit\Regex`, `RegexParser\RegexParser` is `PHPRegex\Parser\RegexParser`, `CompilerNodeVisitor` is `Parser\Printer\PatternPrinter`, `ReDoSAnalyzer` is `Redos\RedosAnalyzer`. The entries below use the 2.0 names; [UPGRADE-2.0.md](UPGRADE-2.0.md) maps every 1.x name to its 2.0 one.
- The public API is declared: every class outside it says `@internal`, and [the backward compatibility promise](docs/reference/backward-compatibility.md) lists what each release may change. The classes of the CLI and of the language server, the bridges' commands, the lint rules, the lint diagnostics (`Diagnostic`, `DiagnosticType`: read lint results through `PatternLinter::getIssues()` or the CLI's JSON), the transpiler's targets, the lexer, the grammar and the validator are internal; call `Regex::validate()` or `RegexParser::validate()` rather than the validator.
- Result objects (`RedosAnalysis`, `CaptureShape`, `EquivalenceResult`, …) are built by the library: their constructors are `@internal`, so a minor release may add a parameter. Each package requires its `php-regex/regex-*` siblings at its own version (`self.version`), so they are installed and updated together.
- Enum cases are in PascalCase, and `TokenType`, `GroupType` and `QuantifierType` drop their `T_` and `T_GROUP_` prefixes: `TokenType::T_LITERAL` is `TokenType::Literal`, `GroupType::T_GROUP_CAPTURING` is `GroupType::Capturing`, `ReDoSSeverity::HIGH` is `RedosSeverity::High`. Values are unchanged.
- `LiteralExtractionResult::$confidence`, from `Regex::literals()`, is a `LiteralConfidence` enum (`High`, `Medium`, `Low`) where it was the string `'high'`, `'medium'` or `'low'`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `Regex::highlight()` throws `InvalidRegexOptionException` on a format other than `console` and `html`, `OutputFormat::Text` included, where it wrote console output; `explain()` and `transpile()` name the values they take when they refuse one.
- The Symfony console command `regex:compare` no longer answers to `debug:compare`.
- The options of `Regex::create()` and `RegexParser::create()` are the closed shape `OptionsArray`: PHPStan reports a misspelt key or a value of the wrong type where the array is written, where `array<string, mixed>` let any array through. Options read from a file go through `ParserOptions::fromArray()`, which checks every key and value, and the new `Regex::fromOptions()`, the counterpart of `RegexParser::fromOptions()`.
- The array options of `optimize()`, on `Regex` and on `Optimizer`, are the closed shape `OptimizerOptionsArray` exported by `OptimizerOptions`, where `array<array-key, mixed>` let any array through: PHPStan reports a misspelt key or a value of the wrong type where the array is written.
- `RailroadSvgRenderer` is a `string` visitor: accepted on a pattern's `RegexNode` it gives the diagram, on any other node the empty string. Its layout, which its `visit*()` methods returned as geometry arrays for every inner node, moved to an internal class, with the `Svg*` type aliases; the API reference no longer lists the aliases internal classes export.
- `AnalysisReport` names its parts as nouns: `$optimization`, the one optimization result, and `$explanation` replace `$optimizations` and `$explain`. `DelimitedPattern` is built with its constructor and spelled with `(string)`: `fromRaw()` and `toString()`, which repeated them, are gone.
- `PcreLimits`, `RedosOptions` and `SolverOptions` refuse a limit that means nothing where they are built, with `InvalidRegexOptionException` naming it, as `OptimizerOptions` already did: a backtrack or recursion limit, a state cap or a step cap below 1, a bounded-repeat cutoff or a transition budget below 0.
- `ConfirmationOptions` refuses an out-of-range value with `InvalidRegexOptionException` naming it, as `RedosOptions` and `SolverOptions` do, where it raised the value to its floor in silence: a subject length, a step or iteration count or a PCRE limit below 1, a `maxInputLength` below `minInputLength`, a `timeoutMs` below 1.0 or `NAN`, a `previewLength` below 0. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `PatternLinter` gives its findings one way, `getIssues()`: `getWarnings()`, their messages, and `getFullPattern()` are gone. Its constructor takes the rules to enable only, and `Transpiler`'s the parser only: the rule and dialect registries they also took are internal.
- The exceptions read through their public readonly properties: `RegexException::getErrorCode()`, `getPosition()` and `getSnippet()` and `SemanticErrorException::getHint()`, which repeated `$errorCode`, `$position`, `$snippet` and `$hint`, are gone. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `RedosAnalysis` reads through its properties as the other results do: `$confidence` is never null (`Low` when nothing raised it) and replaces `confidenceLevel()`, `$culpritNode` replaces `getCulpritNode()`, and `getPrimaryHotspot()` is `primaryHotspot()`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- One concept takes one parameter name, which named arguments make part of the API: `$regex` for a pattern with its delimiters (`Transpiler::transpile()`, `LanguageSolver::acceptsPrefix()`, `language()` and `compile()`, `TrivialMatchClassifier`, `RedosRepairer::repair()` and `PcreEngine` took `$pattern`), `$ast` for a parsed tree, `$subject` for the text matched against and `$parser` for the `Transpiler`'s parser. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `Regex::tokenize()` is an instance method, and it and `RegexParser::tokenize()` return a `list<Token>` read for the instance's target, where the facade's static method returned the parser's internal cursor, `TokenStream`, and lexed for the running PHP whatever the instance judged. `TokenStream` and the `Token` constructor are internal.
- `RemovableCacheInterface::clear()` takes no argument and empties the cache: the parser stores a tree under a seed of its own, not under its regex, so `clear('/foo/')` removed nothing. `CacheInterface::generateKey()` names its parameter `$seed`, and the `keyFactory` of the PSR adapters receives that seed. `FilesystemCache::clear()` removes the files it wrote and the directories they leave empty, where it emptied the whole directory, files of other owners included.
- `--format` calls the terminal rendering `console` on every command: `regex explain` takes `console` or `html`, `regex diagram` `console` or `svg`, `regex highlight` `auto`, `console` or `html`, and Laravel's `regex:explain` `console` or `html`. The former `text`, `ascii` and `cli` values are refused as usage errors (exit code 2) naming the values each command takes, and `help highlight` no longer advertises a value the command refused.
- Every command writes a usage error (exit code 2) to stderr, with its usage line: an unknown option or format, a missing pattern, an invalid library option, a file that cannot be read or written, an unknown command for `help`. Only `lint` did; the others wrote it to stdout, where a redirection such as `regex diagram ... --format=svg > out.svg` captured it. The JSON error envelope stays on stdout.
- The configuration takes the PHPRegex name: the Symfony bundle is `PHPRegexBundle`, configured under `php_regex`, with services and parameters named `php_regex.*`; the PHPStan parameter is `phpRegex`; the Laravel provider is `PHPRegexServiceProvider`, its config `config/php-regex.php` (key `php-regex`, publish tag `php-regex-config`), its container entries `php-regex.*`. A `config/regex-parser.php` left from 1.x is no longer read, and the provider raises a deprecation that says so.
- `validate()` lets an exception that is not the library's through instead of turning it into an invalid-pattern result.
- The aliases that kept the names of moved classes resolving are gone, with the file Composer loaded on every request to register them; the moved classes answer to their new names only. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- The PHPStan extension reports by default only a pattern the target PHP refuses while the PHP running PHPStan compiles it (`regex.invalidForTarget`): PHPStan's own `regexp.pattern` already reports the others. Lint rules and ReDoS analysis are opt-in through `rules.neon`; the legacy and dead parameters are gone, and ReDoS findings share one identifier, `regex.redos`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- The PHPStan ReDoS message is `Exponential backtracking (ReDoS): <pattern>`, `Polynomial backtracking (ReDoS): <pattern>` or `Potential backtracking (ReDoS): <pattern>`, where 1.x said `Potential ReDoS risk (theoretical) (severity: …, confidence: …): <pattern>` or `Confirmed ReDoS risk (…)`. The text of each message stays the same for all of 2.x, though an error may appear, disappear or change class when the analysis improves; the severity, how the verdict was reached and the attack moved to the tip. Baselines holding a ReDoS error must be regenerated once. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `RedosAnalyzer`, `LanguageSolver`, `Transpiler` and `AnalysisService` take a `RegexParser` instead of a `Regex`, and `RegexAnalysisService::getRegex()` is `getParser()`. `CharSet` and `CharSetAnalyzer` moved from `RegexParser\ReDoS` to `PHPRegex\Parser\Analysis`, `CharSet` as `ByteCharSet`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- The automata solver has one entry point, `PHPRegex\Automata\LanguageSolver`: `RegexSolver`, `RegexLanguageSolver`, `RegexSolverInterface` and `RegexSolverCompilerInterface` are gone. `intersectionEmpty()` is `intersection()`, `prepare()` is `compile()`, which returns the `Dfa`; `subsetOf()` and `equivalent()` keep their names, and the result classes are unchanged. The constructor takes the parser and a DFA cache, no longer a `RegularSubsetValidator` or a `DfaBuilder`. Every class of `PHPRegex\Automata` but `LanguageSolver`, `SolverOptions`, `MatchMode`, the two algorithm enums, the three result classes, `Dfa`, `DfaCacheInterface` and `InMemoryDfaCache` is `@internal`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- Error codes are an enum, `PHPRegex\Parser\ErrorCode`: `RegexException::$errorCode` holds one and is never `null`, and `ValidationResult::$errorCode` is `?ErrorCode`. Every syntax error has its own code where 1.x said `parser.error` or `lexer.error`, and every semantic error its own where it said `regex.semantic`; those three values are gone. `RegexException`, `LexerException`, `ParserException` and `SemanticErrorException` take the code as a required second argument; `ComplexityException`, `TranspileException` and `SampleGenerationException` take an optional `ErrorCode`. `regex.callout.invalid_type`, which no pattern could raise, is gone. The CLI's JSON output and lint problems still carry the string value. The language server publishes a pattern it cannot parse under that code instead of `regex.parse.error`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `Regex::optimize()` and `Optimizer::optimize()` take an `OptimizerOptions` value or an array keyed in snake_case, as `Regex::create()` is; an unknown key or a value of the wrong type throws `InvalidRegexOptionException` where it was ignored or cast. `autoPossessify` is `possessive` and `allowAlternationFactorization` is `factorize`, as every configuration already named them. `LintRequest::$optimizations` and `AnalysisService::suggestOptimizations()` take an `OptimizerOptions`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `RegexParser::clearCaches()` and `Regex::clearCaches()` replace `clearValidatorCaches()`, which is gone from both: they empty every process-wide cache of the library, not only the validator's. Every such cache is bounded as well. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- What the library throws says whose mistake it is. A mistake of the caller throws an exception implementing `PHPRegex\Parser\Exception\ExceptionInterface`: `Regex::explain()` with an unknown format throws `InvalidRegexOptionException`; an unknown formatter, a failed lint worker and a report JSON cannot hold throw the new `PHPRegex\Linter\LintException`; an unknown graph or highlight format and a self-update that cannot go on throw the new `PHPRegex\Cli\CliException`; the sample generator throws `SampleGenerationException` where it threw `\LogicException` or `\RuntimeException`, and `generate()` throws it for a pattern the library judges invalid, before drawing any sample. A bug of the library, a token stream read past its bounds included, throws a plain `\LogicException`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `LanguageServer\Server::run()` returns the code to exit with instead of ending the process; `bin/regex-lsp` exits with it.
- Runtime validation (`runtime_pcre_validation`) reports PCRE's message without the "Compilation failed: " PHP puts before it, and a pattern that compiles but fails on the empty subject, as `/(?R)/`, is valid.
- The ReDoS confirmation reports the JIT setting it ran under, off (`jit_setting` is `false` in JSON), and the limits of its options, where it reported the ini values.
- `regex analyze` and `regex debug` refuse `--redos-no-jit`: the ReDoS confirmation always runs without JIT, so the option changed nothing. `ReDoSConfirmOptions::$disableJit` and `ReDoSConfirmation::$jitDisableRequested` (`jit_disable_requested` in JSON) are gone.
- `ValidationResult::$error` is the message alone: the caret snippet is no longer appended to it, and stays in `$caretSnippet`. The CLI and the Artisan commands print both; `regex:transpile --format=json` carries the snippet as `validation.caret_snippet` in its error envelope. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- Every offset counts from the first character of the pattern body, as PCRE2's do: a modifier error points at the modifier PHP refuses, counted past the body and its closing delimiter, and a pattern with no body has no offset. The caret snippet of a fault outside the body still shows the whole pattern, delimiters included, and the language server places its diagnostics on the character at fault. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `CacheInterface` stores trees: `write(string $key, RegexNode $ast)` and `load(string $key): ?RegexNode`; `getTimestamp()` is gone. `CachePayloadDecoder`, `FilesystemCache::defaultDirectory()` and the file extension argument of `FilesystemCache` are gone; the default cache is `ArrayCache`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `SequenceNode::$children` and `AlternationNode::$alternatives` are lists (`list<NodeInterface>`): both constructors renumber the array they are given, in the order given, where 1.x kept its keys. Code that kept a key across `array_filter()` and read it back on the node it built reads by position instead. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `regex.json` is read strictly: an unknown key or lint rule id, a value of the wrong kind, or a removed 1.x key (`rules`, `redosMode`, `redosThreshold`, `redosNoJit`, `optimizations`, `minSavings`, `checks.redos.noJit`) is an error naming its replacement, every error of both files is reported at once, and the lint command exits with code 2. `checks.redos`, `checks.optimizations` and `checks.lint` are objects only; `checks.redos.mode` loses `off`; only `enabled` switches a check on; a list in `regex.json` replaces the one in `regex.dist.json` whole. `regex.schema.json` is written from the definition the command validates against. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- The lint command judges for the project's lowest PHP: `--php-version`/`--pcre-version`, else `phpVersion`/`pcreVersion` in `regex.json`, else `composer.json` (`config.platform.php`, then the floor of `require.php`), else the running PHP; PHP 7.3, the first PHP on PCRE2, is the oldest judged, with the PCRE2 its sources bundle (10.32 for 7.3, 10.33 for 7.4, 10.35 for 8.0); a release older than 10.39 is judged with the 10.39 rules, with a note that says so. PHP 7.2 and earlier ship PCRE1 and are never judged: a `require.php` that also allows PHP 7.3 or later (`^7.1|^8.0`, `>=5.4`) is judged from the lowest such PHP, with a note that the versions below 7.3 are not judged, even under a `config.platform.php` below 7.3, which only pins the PHP Composer resolves the dependencies for; a version below 7.3 named by `--php-version`, `phpVersion` or a bridge setting, or a `composer.json` that allows no PHP of 7.3 or later, is refused: the command exits with 2 and the JSON error envelope names the stage `target`. The JSON report names it under `target`; the console banner shows it as a `Target` row under `Runtime`; the GitHub, Checkstyle and JUnit formats print it on stderr. When the PHP comes from `require.php`, the patterns are also validated on the later PHP versions the constraint allows (below), so a project green on its floor may turn red on its ceiling. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- A ReDoS threshold is read the same way everywhere, by the new `RedosSeverity::fromConfig()`: `low`, `medium`, `high` or `critical`, in any case. `safe` and `unknown` are refused, as is any other word, with the value quoted: by `--redos-threshold` of the `lint`, `analyze` and `debug` commands and of `regex:analyze` and `regex:security`, by the Symfony and Laravel configurations, by the PHPStan rule (even with ReDoS off), and by `AnalysisService`, which throws `InvalidRegexOptionException` where it fell back to `high`. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- Symfony bundle: `runtime_pcre_validation` defaults to `false` instead of `%kernel.debug%`; `exclude_paths` is `exclude`; `analysis.ignore_patterns` is merged into `redos.ignored_patterns`; `analysis.redos_threshold`, never read, is gone. A 1.x key stops the container compile with the key that replaces it. New `php_version` and `pcre_version` set the target of `regex:lint`, which otherwise reads `composer.json` in `%kernel.project_dir%`, like the standalone lint command; its JSON report names the target, and it never uses `runtime_pcre_validation`. The `php_regex.regex` service keeps judging for the running PHP. See [the Symfony guide](docs/guides/symfony.md).
- Laravel: `config/php-regex.php` follows the same names (`exclude`, `redos.ignored_patterns`, no `analysis.redos_threshold`), `runtime_pcre_validation` defaults to `false` instead of `APP_DEBUG`, and `php_version` / `pcre_version` set the target of `regex:lint`, which otherwise reads `composer.json` at `base_path()`. A published file lacking keys takes the package default for each one, inside sections too; `regex:lint` warns about a 1.x key it still finds. See [the Laravel guide](docs/guides/laravel.md).
- The language server judges for the workspace's target, resolved at `initialize`: `initializationOptions.phpVersion` / `pcreVersion`, else `regex.json`, else `composer.json` of the first workspace folder, else the running PHP; it logs the target with `window/logMessage`. See [the language server guide](docs/guides/lsp.md#target-php-and-pcre2).
- The lint command exits with code 2 on a configuration or usage error (an unknown `--format` included), prints errors on stderr, or as the error envelope `{"error": ..., "stage": ...}` on stdout under `--format=json`, and keeps its progress and status lines out of a JSON report. `--redos-mode=off` (use `--no-redos`) and `--redos-no-jit` are refused; the ReDoS confirmation always runs without JIT.
- Every CLI command exits with the lint command's codes: 0 when it found nothing wrong, 1 when the patterns or files it judged have a problem, 2 when the command line or the configuration cannot be used. A usage error (an unknown command or option, a missing pattern or option value, an unknown `--format` or `--target`, an invalid `--php-version`, a removed option, an unreadable `--input-file` or `regex.json`) exits with 2 where it exited with 1, and `regex` without a command with 2. `analyze` and `parse --validate` exit with 1 on an invalid pattern, `debug` on an invalid pattern in every format, a semantic error such as `/(?<=a+)b/` included, `analyze` and `debug` on a ReDoS risk `--redos-mode=confirmed` confirms at high severity or more, and `redos` on a pattern PHP refuses; all four exited with 0. `debug` stops on a `regex.json` it cannot read instead of ignoring it. `parse`, `validate`, `explain`, `diagram`, `highlight` and `graph` refuse an option they do not know and read options before the pattern. The Symfony and Laravel console commands exit with 2 (`Command::INVALID`) where an option or the configuration cannot be used. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `regex lint` refuses a path that does not exist, where it scanned nothing and exited with 0: a path given on the command line is a usage error, a path listed in `regex.json` a configuration error, both with exit code 2 and, in JSON, the error envelope with stage `usage` or `config`. A `--baseline` file that is missing or holds no baseline is a usage error too, with stage `usage`, where it was ignored. See [UPGRADE-2.0.md](UPGRADE-2.0.md#json-output).
- `lint --format=github` writes `col=` as the column of the pattern in the file, where it wrote the position of the issue inside the pattern, or `1`; `col=` is left out when the column is unknown. `%` is escaped as `%25` in the message too, and `:` and `,` as `%3A` and `%2C` in the `file` and `title` properties, as GitHub's format requires. The Checkstyle `column` is the same file column, left out when unknown. See [UPGRADE-2.0.md](UPGRADE-2.0.md#github-and-checkstyle-reports-point-at-the-pattern).

### Security

- `regex.phar` is built by a GitHub Actions workflow from the release tag, never on a maintainer's machine, and carries a build provenance attestation: `gh attestation verify regex.phar --repo php-regex/php-regex` checks that a downloaded phar is the one that workflow built. The release is published only once the phar and its checksum are attached.
- The default cache wrote parsed trees as PHP files under the shared system temp directory and `include`d them: another local user could plant a file there and have it run, or change a verdict. Nothing is written to disk by default any more (the latest 1024 trees are kept in memory), `FilesystemCache` only runs where a directory is named, stores data read back with a class allowlist instead of code, creates its directories for their owner only (`0700`, files `0600`) without touching the process umask, and ignores a directory another user owns or others can write to.

Every set it matches — classes and ranges, `\w\s\d`, the dot, POSIX classes, `\p{...}` properties and scripts, Perl extended classes `(?[ ... ])` and case-insensitive folds — is asked from the PCRE2 that runs in the PHP process, so the solver, the ReDoS engine and every consumer read the same characters. POSIX classes (`[[:alpha:]]`, negated included), Unicode properties (`\p{L}`, `\P{L}`, scripts such as `\p{Greek}`), extended classes with their set operations and the `\C` byte escape are answered where the old conversion refused them outright. Verdicts are engine-relative and say which engine gave them: `EquivalenceResult`, `SubsetResult` and `IntersectionResult` carry `pcreVersion`. Under `/u` the sets cover the code points minus the surrogate block U+D800–U+DFFF, which no valid subject contains — a one-time shape change of the character sets, announced here; the pinned verdicts did not move.
- One refusal taxonomy: a pattern outside the regular subset raises `ComplexityException` with one message per reason — backreferences, subroutine calls, callouts and control verbs (and `\X`); conditional groups; lookarounds; atomic groups (and `\R`); word boundaries, `\K`, `\G` and anchors away from the edges of an alternative; a possessive quantifier the follower rule cannot prove inert; a flag outside `i`, `s` and `u`. The parallel message set of the AST-side conversion ("Unsupported character type: …", "Unsupported regex node in automata conversion.", …) is gone. `^` and `$` keep their two messages, and `\A`, `\z` and `\Z` are now read at the outer edges of an alternative, as `^` and `$` are.
- `PHPRegex\Parser\Hir`, a normalized form of a pattern next to the AST, internal for now. `HirTranslator` turns a `RegexNode` into nodes that say what the pattern matches with the syntax gone: options applied where they hold, every character, class, dot, escape or caseless letter as one `CharSet` the running PCRE2 was asked for (so `\w` under /u, `\p{L}`, `[[:alpha:]]` and `k` under /iu, which also matches the Kelvin sign, are exact for the PHP that runs), groups that only group removed, quantifiers as repetitions with their bounds and greed, and backreferences, subroutine calls and verbs kept as opaque nodes around their AST node. Each node carries `Properties`, worked out once when it is built: minimum and maximum length, nullability, the sets of first and last characters, the literal prefix and suffix, the capture count, and whether the node is a regular expression in the textbook sense. `CharSet`, `ClassSetProvider` and `Utf8` moved from `PHPRegex\Redos\Internal\Backtrack` to `PHPRegex\Parser\Hir`, so that every library shares one set of characters and one engine oracle; `ClassSetProvider::query()` takes the options a pattern opens with, `(*UCP)` or `(*CR)`, which change what a class matches.
- Proven ReDoS verdicts. `RedosAnalyzer` builds an automaton of PCRE's backtracking, alternatives and quantifiers in PCRE's order, and proves the complexity class of one match attempt: linear (`safe (proven)`, given only when the model holds no exponential and no polynomial ambiguity at all), polynomial with its degree, or exponential; a vulnerable pattern comes with a witness, the input `prefix . pump x n . suffix` that drives the worst case, rendered as PHP (`"a" x n . "!"`). Atomic lookaround bodies are analysed as their own searches, `\b`, `\B` and the anchors exactly at every attempt start, classes under `/u` and `/i` from the running PCRE2, and the second search `preg_match()` runs without `$matches` after an empty match is covered. Backreferences, conditionals, recursion, subroutine calls, verbs, callouts, `\X`, `\R`, non-atomic lookarounds, the `xx` option, `\b` and `\B` under two different ASCII scopes in one pattern, a bounded repeat whose body can match empty, a pattern over the analysis budget, an attack crossing an atomic body the model over-approximates, and an ambiguity the analysis cannot witness are judged by the structural heuristics, as in 1.x, and the result says so in `proof` and `abstractions`. New `RedosComplexity`, `RedosProof`, `RedosWitness` and `RedosOptions` (the budget, in states and steps, never in time; it bounds the memory of the analysis too); `RedosAnalysis` gains `complexity`, `degree`, `proof`, `witness`, `replayed`, `abstractions`, `pcreVersion`, `analysisVersion`, `isProvenSafe()` and `headline()`, and its JSON the same keys; `RedosAnalyzer::ANALYSIS_VERSION`; `RedosSeverity::rank()`, one order of severities shared by `RedosAnalysis` and `Heatmap`. See [the ReDoS guide](docs/guides/redos.md).
- Confirmed ReDoS mode replays an exponential witness on the running PCRE2, without the JIT and under the backtrack limit of `ConfirmationOptions`, one pump more at a time up to 64, within a fixed amount of work. It tries several suffixes, the literals a match needs included, and publishes the one that reproduced; only an exhausted backtrack limit counts. `replayed` says whether it reproduced. A polynomial verdict is reported but never replayed. A proven vulnerable verdict has `high` confidence only once replayed.

### Changed

- Reading and judging a pattern is faster, with the same tokens, trees, errors and offsets: on about 24,000 distinct patterns gathered from open-source PHP projects (PHP 8.4, PCRE2 10.49, an Apple M1 Max, the median of per-pattern medians), `validate()` of a pattern seen for the first time takes about 60 µs where it took about 110 µs (about 12 times PCRE's own compile and JIT, where it was 22), `parse()` about 43 µs where it took 84, and `tokenize()` about 23 µs where it took 41. A `RegexParser` keeps the results of the last 1024 patterns it validated, so a pattern validated again by the same instance, as the lint run and its ReDoS analysis do, costs a lookup (about 0.1 µs) where it walked the tree again (about 22 µs); such a call does not reach the AST cache, which `getCacheStats()` then does not count, and `clearCaches()` empties the results.

- `regex.lint.group.alwaysEmptyCapture` reports the same groups in a fraction of the time: it asks the automata about a capturing group only when no subject built from the pattern shows the running engine filling the group, which is the case for about nine groups in ten, and keeps each answer per pattern and target for the next lint of the same pattern. On about 23,500 valid patterns gathered from open-source projects (PHP 8.4, an Apple M1 Max), the rule takes about 3 s where it took about 25 s, and the default lint rules together about 16 s where they took about 38 s.

- The set of characters a Unicode class matches, which the ReDoS analysis, the automata and the lint rules that ask them read from the running engine by matching the class over every code point, is put together from what its members match: each type, property or POSIX class is read once per process, whatever class holds it, where each class was read whole by its text, so `[\w-]`, `[\w.]` and `[\w\-]` were three reads. A caseless class is put together from members the engine folds one by one, a caseless ASCII character is itself and its other case (but "k" and "s"), and a general category other than Lu, Ll and Lt is read once with and without `i`. A negated type or property (`\S`, `\P{L}`) is the rest of the alphabet, the dot matches the same caseless and every character under `s`, a negated POSIX class is the rest of the POSIX class, and every general category, `\p{Lu}` to `\p{L}`, comes from one read of all thirty: so do `[[:alpha:]]`, `[[:alnum:]]`, `[[:digit:]]`, `[[:lower:]]`, `[[:upper:]]` and `[[:cntrl:]]` under `/u`. A read over every code point runs with the JIT, about seven times faster, unless its class holds a parenthesis. Every set so put together, and every read with the JIT, was compared with the interpreter's read of the whole class on PCRE2 10.39, 10.40, 10.42, 10.44 and 10.49, about 12,000 classes each, and found equal. On the 1,800 Unicode patterns among about 24,000 gathered from open-source projects, the ReDoS analysis reads under 60 sets where it read about 660, and takes about 1.5 s where it took about 20 s.

- The language server keeps what it found in each pattern, per target, for the session (the latest 4096 patterns): a change analyses only the patterns whose text it changed and moves the findings of the others, where it linted every pattern of the document again. A keystroke inside a pattern a call takes whole is read in place, the rest of the document standing as it stood, where every change read the document again; any other change still does. An edit to one pattern of a document holding about 330 takes about 5 ms where it took about 380 ms.

- `ArrayCache`, the default AST cache and the memory in front of a directory or a PSR pool, drops the tree read or written longest ago, where it dropped the one written first: a pattern read again and again stays among patterns met once.

- A lint rule whose every identifier is off, by default or in `checks.lint.rules`, no longer runs: it ran on every pattern and its findings were dropped. `quantifier.uselessLazy` was the costly one; with it, the default lint rules on the same patterns take about 9.5 s.

- The internal classes moved out of the `Internal` namespaces, each to the namespace of what it does (`Parser\Syntax\PatternParser`, `Parser\Text\Ascii`, `Linter\Parallel\WorkerCount`, `Redos\Backtrack\BacktrackProver`, …) or to its package root; they stay `@internal`, and the tag alone marks a class outside the API.

- The rules of `RegexSetList::PCRE_UPGRADE` (`EscapeLiteralBraceRector`, `AlphabeticAssertionToClassicRector`, `EscapeNulByteRector`, `PossessiveRepeatOnceRector`) rewrite the declaration of a private class constant whose class reads it only as a pattern they read, written `self::NAME`: `private const PATTERN = '/a{,3}/'` read by `preg_match(self::PATTERN, $s)` becomes `'/a\{,3}/'` for code that targets PHP 8.3 or earlier, where every constant was left as it is. Public, protected and global constants are still left, as code elsewhere may read them, and so is a private one its class also reads another way, or held by a class that uses a trait.

- The check of a rewrite, in `regex lint`, the bridges' `regex:lint` and `Optimizer::optimize()` with `verify_with_automata`, proves two more kinds of rewrite where the match solver does not read the pattern. The branches at the top of a lookbehind are read together, as the lookbehind holds where some string one of them matches ends, whatever their order: `(?<![\xC2-\xDF]|[\xE0-\xEF]|[\xE0-\xEF][\x80-\xBF])` into `(?<![\xC2-\xDF\xE0-\xEF]|[\xE0-\xEF][\x80-\xBF])` is offered, when no group stands in the branches and each matches strings of one length on both sides, which every PCRE2 release accepts there; the alternatives of a group inside a lookbehind are not read that way, as releases before 10.43 refuse them for their two lengths. And two runs of parts of other counts are paired by the parts both keep, so `/(.*-----BEGIN CERTIFICATE-----.*-----END CERTIFICATE-----){50}$/Uims` into `/(.*-{5}BEGIN CERTIFICATE-{5}.*-{5}END CERTIFICATE-{5}){50}$/Uims` is offered, each run of dashes proven alone.

- The PHPStan extension, the Psalm plugin and the `regex` commands that read one pattern (`validate`, `analyze`, `explain` and the others) judge the target `regex lint` judges: a PHP below 7.3, which ships PCRE1, named by `--php-version`, `phpRegex.phpVersion`, PHPStan's `phpVersion`, `<phpVersion>` or Psalm's PHP version, is refused with the lint's error (`phpVersion names PHP 7.1: PHP 7.2 and earlier ship PCRE1, ...`; exit code 2 and the envelope with stage `target` for a command), where PHPStan judged it as given and Psalm raised it to 7.3. Laravel's `regex:compare` prints every key whatever the method, `null` where the method fills none. The firewall finding of `regex:analyze` labels the ReDoS severity `Severity` again, where it said `CheckOutcome`.

The optimizer's match check gives up on a work budget of its own and hands the rewrite to the language check: verifying the rewrite of craftcms's 1,600-byte mobile user-agent list takes 0.5 s instead of 4 s.

A pattern with such classes reaches the budget sooner, with the same `ComplexityException` naming its `limit`.

- `regex lint`, and `regex:lint` in Symfony and Laravel, read each pattern once when they suggest optimizations: the optimization step takes the tree and the validation the analysis step built, sent back by its workers with their findings, where it parsed and validated every pattern again. In one process, the optimization step takes about half the time it did.
- `regex lint`, and `regex:lint` in Symfony and Laravel, build each automaton once per run: the lint rules that ask the automata share one DFA cache, where each rule kept its own for one pattern. On a project repeating its patterns, the automata rules run about three times faster. `InMemoryDfaCache` is bounded (1000 automata, the older half dropped when full) and `clearCaches()` empties it.

The suggested rewrite of a pattern under `x` whose source text is not known (a tree from a cache that dropped it, or built by code) is printed this way.

The console shows the tabs `x` skips as the indent they are, up to the next stop of four columns, and spells `\t` only a tab that is a character, in a class or in `\Q...\E`.

The console format of `regex lint` draws its progress and its steps on stderr, so that a report redirected to a file holds no progress frames; the bridges draw their bars on stderr too. The inline ignore markers are read by the workers, and the source of a file is read once for all its issues, where the main process read them again after the analysis. The `Processes:` line under the report counts the workers the run started.

The three commands counted CPUs three different ways, from `hw.ncpu`, `wmic` on Windows or `swoole_cpu_num()`; none is read any more. A worker that fails or exits stops the run with exit code 1 and names the files it was reading; the JSON envelope says `"stage": "analyze"`.

Every key is snake_case: the lint report's `fileOffset`, `issueId` and `type` are `file_offset`, `issue_id` and `severity`, its `validation` reads `is_valid`, `complexity_score`, `caret_snippet` and `error_code` as `analyze` does, and `analyze`'s `valid` is `is_valid`. Every command prints one pretty-printed document ending with a newline, and every failure the error envelope `{"error": ..., "stage": ...}`, with stage `usage`, `config`, `collect`, `pattern` or `internal`; a usage error is one too once `--format=json` or `--json` is anywhere on the command line. `--quiet` silences the human status lines only: `lint` prints its JSON, GitHub, Checkstyle and JUnit reports under it, as Symfony's and Laravel's `regex:lint` do, where it printed nothing. `lint --json` is short for `--format=json`, and `transpile` reads `--format json` as well as `--format=json`. `--format` values are case-insensitive everywhere, Symfony's and Laravel's commands included, and the last `--format` or `--json` on the command line wins. Results are sorted by file, line and column whatever `--jobs` says, and `file` is relative to the working directory. `runtime.jit` and `confirmation.jit_setting` are bools. The entries of the baseline file hold `{file, line, column, issue_id, message, severity, pattern, pattern_hash}`, the keys of the lint issue. Symfony's and Laravel's `regex:transpile` print the CLI's document and envelope: Laravel's `{source, target, result, flags, warnings, compatible}` payload and its `{error, details, snippet}` errors are gone, and its `--target` takes the transpiler's targets, `javascript` (or `js`) and `python` (or `py`): `ruby`, `go`, `rust`, `java`, `csharp` and `swift`, listed but never translated, are a usage error. Symfony's and Laravel's `regex:lint` print a JSON failure as the envelope with its stage, where they printed `{"error": ...}`, or a text error for an option Symfony could not use. See [UPGRADE-2.0.md](UPGRADE-2.0.md#json-output).
- A rewrite the optimizer verifies (`verify_with_automata`, and every rewrite that adds a possessive quantifier or an atomic group) must now write the same `$matches` as the pattern, checked by `LanguageSolver::matchEquivalent()`, where it had only to match the same strings: `/(a|ab)/` and `/(ab|a)/` pass the second check and fail the first. A pattern the match solver cannot read, or too large for it, keeps only a rewrite that reads as it does (`[0-9]` for `\d`): the strings both match prove no `$matches`, as `/a(?!b)/` and `/a/` show on `"ab"`, and `/(?:a|ab)(?!c)/` and `/(?:ab|a)(?!c)/` as well. `LanguageSolver::matchEquivalent()` reads a possessive quantifier that never has to give anything back, a body that matches one fixed way with nothing after it starting like it (`/a++b/`, `/\d++a/`), so those rewrites are proven by it.
- The PHPStan rule no longer reports ReDoS on a call whose subject PHPStan knows to be constant — a literal, a constant, a concatenation or an array of them: such a call backtracks the same way on every run, or never, and no input can reach it. `preg_match('/(a+)+$/', 'fixed')` is silent; `preg_match('/(a+)+$/', $input)` is still reported. A baseline holding a `regex.redos` error on a constant subject reports it as unmatched.
- `/x*+(ab)/` is answered — it was refused by an accident of nested-sequence flag handling — and a flat chain of possessives such as `/x*+ab*+/` is refused: the second possessive sits beyond the next part, which the follower rule cannot see across, and answering it was not sound. `b++(?i:B)` is refused for the right reason now: the rule reads an inline caseless follower case-blind, where it refused the inline flag itself before.
- A pattern that names a surrogate code point (`\x{D800}`, a class member, a range endpoint) under `/u` is refused: PCRE refuses to compile it, and the old conversion answered it with a witness built on a corrupted range table. The possessive-follower rule now reads past capture, alternation-branch and repetition boundaries — `/(a++b?)a/` was vouched and the optimizer shipped it where the language changes — and comparisons between a byte and a code-point pattern keep their witnesses: `/k/iu` and `/k/i` were wrongly called equivalent because the search skipped the Kelvin sign one side cannot match.
- Counter-example strings above byte 0x7F in byte mode (without `/u`) are the raw bytes themselves, where they were wrongly UTF-8-encoded; the engine reads them byte by byte and so does the solver.
- Corpus-wide, the solver's pass is as fast cold and faster warm than the AST walk it replaces (measured on the project's corpus: 715 distinct atoms scanned once per process, 1.77 s one-time, about 18 % of the cold pass), while answering 56 corpus patterns the old conversion refused.
- The optimizer ships a rewrite that adds a possessive quantifier or an atomic group only when the automata solver verifies it — whatever `verify_with_automata` says, because the rules that possessify are on by default and the solver refuses the possessive forms it cannot prove safe (`(?:ab|a)+c` stays as written). To verify more of them, the solver's safe-possessive rule now looks past a skippable follower and unions the first characters of everything that follows: `b++` before `c?d` is answered, so that rewrite ships again.
- The corpus is managed by `bin/corpus`, composer-style: `php bin/corpus install` rebuilds `corpus/` exactly at the commits `corpus.json` (now at the root, next to `composer.json`) pins — the directory can be deleted and rebuilt at any time — and `php bin/corpus update` refreshes every checkout and rewrites the pins, where `php corpus/update` did the updating only. The lint snapshot lives in `var/log/corpus.log`.
- ReDoS severities follow the proven class where there is one: exponential is `critical`, polynomial of degree 3 or more `high`, of degree 2 `medium`, linear `safe`. On the repository's corpus of real-world patterns, about 95 % are proven and about 5 % judged by the heuristics; many former `medium` findings are now proven safe, and a smaller number rate higher, each with its attack. A pattern the static validation rejects is never proven safe: `proof: not_analyzed`, severity `unknown`. The default thresholds are unchanged, so a proven quadratic pattern stays below them. As before, only a verdict the running PCRE reproduced, at `high` or more, is an error and makes `analyze`, `debug` and `lint` exit with 1.
- `Regex::generate()` throws `SampleGenerationException` when no sample the running engine matches was found, where it returned its last attempt, a string that does not match. See [UPGRADE-2.0.md](UPGRADE-2.0.md).
- `max_lookbehind_length` (default 255) now only limits variable-length lookbehinds, as PCRE2's own `max_varlookbehind` does: `(?<=a{256})` validates, `(?<=a{0,256})` does not. A fixed-length lookbehind is limited by PCRE's ceiling of 65535 characters, which no option changes. Each top-level branch of a lookbehind is measured on its own.

- Persistent DFA caches are keyed on the version of the code that reads the pattern: `LanguageSolver` adds `RegexParser::CACHE_VERSION` to its cache key, and that fingerprint now also covers the code that turns a tree into automata. A `DfaCacheInterface` kept across an upgrade rebuilds its DFAs instead of answering with ones an older reading built.
- `Regex::analyze()` only reports what the pattern itself causes: a failure that is not one of the library's exceptions now surfaces instead of being written into the report as a pattern error.
- A cache that throws while reading is treated as a cache miss, the way a cache that throws while writing already was.

- `LanguageSolver::findExample()` product-automaton BFS now uses integer pair keys instead of string concatenation, reducing allocation overhead during DFA intersection/subset/equivalence checks.
- **Unified quantifier parsing** via a new `QuantifierBounds` value object. Previously ~20 inline re-implementations disagreed: `{,5}` meant "0 to 5" to the validator but "exactly once" to the length/lint analyzers and "never" to the sample generator; `{ 2 }` (extended mode) was only understood by the validator. All visitors (length ranges, ReDoS, linter, sample/test-case generators, optimizer, explain, railroad) now share one canonical parser.

Patterns like `[\w-_]`, `[\d-z]`, `[a-\d]` — which PCRE rejects at compile time — now fail to parse instead of being silently re-interpreted with a literal hyphen. Literal hyphens at class edges (`[-a]`, `[\d-]`) are unaffected.

- Displayed patterns print every control byte but tab, newline and carriage return, and every byte of invalid UTF-8, as `\xHH`, so a pattern copied from a report reads back as the same pattern, outside `/x` and except for the name given to a verb such as `(*MARK:…)`, where a control byte is spelled out: the octal escapes and `\v` / `\b` printed before mean something else to PCRE (`\v` is the vertical-whitespace class, `\b` a word boundary). Subject strings (`debug --input`, the attack strings of `redos`) and literal text in the tree and railroad views are spelled as plain text: a backslash is doubled and nothing in them is read as pattern syntax.
- The ReDoS heuristic lint issues are more precise. `regex.lint.quantifier.nested` no longer fires on an outer loop nothing at all follows, with an outer minimum of at most 1 and no subroutine call into it (`/(a+)+/`; `/(a+)+$/` and `/(?:a+)+(?=b)/` still fire); on a greedy run of one literal character repeated at most twice before a final `$`, `\z` or `\Z` without `/m` (`/(a+){1,2}$/`; a larger bound, a class, a lazy run or a lookahead still fires); or on an iteration whose inner loop is followed right away by a separator it cannot match, the rest of the iteration matching one way only, wrapping around to the iteration's start for an unrolled loop (`/"[^"\\]*(?:\\.[^"\\]*)*"/`, never exempt under `/i`; elsewhere `/i` compares the separator case-folded). `regex.lint.dotstar.nested` no longer fires when each iteration ends at a newline the dot cannot cross (`/(?:.*\n)+x/` without `/s` or `(?s)`); `regex.lint.overlap.charset` no longer fires on an alternation inside a lookbehind. With the ReDoS analysis on, the three issues are dropped for any pattern the analysis proves linear, a pattern with inline options such as `(?s)` or `(?i-r:...)` included, since the proof reads them as PCRE does. `regex.lint.overlap.charset` is also left out, as the other two already were, for a pattern listed in the ignored patterns or found trivially safe, and for a Symfony route requirement.

### Fixed

- A group, subroutine or condition name that a `\c` ending the pattern, a `\x{}` or, before PCRE2 10.35, a `(?*` cuts short is refused where PCRE2 refuses it, on the backslash or the `(` (`/(?&\c/` at 3, `/(?<a\c/` at 4, `/(?&a\x{}/` at 4), as is a `(?\c` (at 2, past it from PCRE2 10.47), where the escape or the group was reported.
- Java's property names (`\p{javaLowerCase}`, `\p{javaUpperCase}`, `\p{javaWhitespace}`, `\p{javaMirrored}`) and Unicode blocks (`\p{Block=Basic_Latin}`, `\p{blk=ASCII}`, even `\p{Blk=Foo}`) are refused, as `preg_match()` refuses them on every PCRE2 release PHP 8 bundles, where a target of PCRE2 10.40 or later reported them valid. PCRE2 has no Unicode blocks; the error points past the `}`, as PCRE2's does.
- On PHP 8.5 and later, validating a class left open whose range ends on a character past ASCII without `u` (`/[a-é/`) raises no deprecation of `ord()`, and a value in `\x{...}`, `\o{...}` or `\N{U+...}` past what a PHP integer holds raises no warning of a float cast: it reads as the largest integer, where the cast wrapped it to 0 or below.

A `(` that `\c` takes as its character no longer opens a group there either, and a body that never closes is reported as a missing `)` instead of exhausting PHP's backtracking limit. The pretty-printed and compiled forms keep an empty scoped group `(?i:)` apart from the setting `(?i)`.
- A pattern PCRE refuses as too large to compile was reported valid: a group repeated with a count is compiled once per repetition, so `(?:a){8192}` or `((?:a){100}){100}` passes the 64 KiB PCRE takes. The validator now reports `regex.pattern.too_large` when the smallest size PCRE could compile the pattern to already passes that limit; below it, the pattern is left to PCRE.
- `\N{U+...}` above U+10FFFF, as in `\N{U+110000}`, was accepted; PHP refuses it as it refuses `\x{110000}`, with `regex.unicode.out_of_range` at the closing brace.
- `\g-` or `\g+` with no digit after the sign was reported as a relative reference to zero, one character too far; it is now reported as PCRE reports it, a `\g` followed by no reference, on the sign.
- An escaped letter inside a group name, as in `(?<a\y>...)`, was read as the letter and the name accepted as `ay`; PHP refuses any escape in a name, and so does the parser now.
- A pattern with an escape PHP refuses and a structural error further on (`\y(`, `\L\c`, `[a\y`, `[\R(`, `\Pf(`) was reported at the structural error, a missing `)` or `]`; PCRE reads the pattern in one pass and stops on the escape first. Likewise a class left open or a lone `\c` at the end hid a syntax error before it (`+[^`, `)[`). `validate()` now reports the error PCRE meets first; `parse()` is unchanged.
- The pretty-printed form of a pattern showed a modifier setting such as `(?i)` as an empty scoped group, `(?i:)`, which applies to nothing; it now shows `(?i)`.
- `\k` inside a class (`[\k]`, `[a\k<n>]`) was accepted for every target; PCRE2 reads it as the letter only from 10.45, which no PHP release bundles yet, and refuses it before. It is now refused unless the running PHP links PCRE2 10.45 or newer.
- The body of `(*pla:...)`, `(?*...)` and the other alphabetic assertions was never checked for escapes PHP refuses (`(*pla:\y)`, `(*pla:\U)`, `(*pla:[\B])`), and the body of `(*sr:...)` was not checked at all (`(*sr:a{2,1})`); both are now checked like the rest of the pattern. An error found inside such a body is reported at its offset in the whole pattern, not in the body.
- `\b{g}` and `\B{g}` were read as grapheme-boundary assertions, which PCRE2 does not have: it reads a word boundary followed by the text `{g}`. They now parse that way, so `\B{g}+` (which repeats the `}`) is no longer refused.
- A quantifier after `(*LIMIT_MATCH=n)`, as in `(*LIMIT_MATCH=10)+`, was accepted; PHP refuses to repeat it, as it refuses to repeat the other start-of-pattern settings.
- The body of `(*pla:...)`, `(*atomic:...)`, `(*script_run:...)` and the other alphabetic assertions ended at the first `)` outside a nested group, even one that was escaped, in a class, quoted by `\Q...\E` or in a `(?#...)` comment: `(*pla:\))` and `(*pla:[)])` were refused, `(*pla:\Qa)` accepted. It is now read as any group body is.
- Error offsets now follow the PCRE2 release that judges the pattern. PCRE2 10.47 reports most syntax errors past the character at fault rather than on it, and 10.45 moved a few; the library reported the newer offset for some errors and the older one for others. For a `php_version` target, whose bundled PCRE2 is 10.40 to 10.44, it now reports the older offsets, and without a target the offsets of the PCRE2 the running PHP links. On random malformed patterns, offsets for a PHP 8.4 target went from 58% to 94% agreement with PCRE2 10.44. A count with nothing to repeat, as in `{2,1}` or `{65536}`, is now refused on its numbers, as PCRE reads them first, and the unmatched `)` offset moved in PCRE2 10.47, not 10.46.
- `validate()` reports the error PCRE meets first in more cases: an unknown POSIX class or a reversed range in a class a syntax error follows (`[[:foo:]](?(?(`, `[z-a](?#`), an item refused before its count (`[z-a]{2,1}`, `\pX{65536}`), numbers out of order or past 65535 after an anchor, a callout or another quantifier (`^{2,1}`, `a++{65536}`), and an escape where `(?` expects an option letter (`(?i\y`, refused on the backslash). From PCRE2 10.45, a property name holding a character no name holds, as in `\p{L!}`, is malformed (`regex.unicode.property_malformed`) and refused past that character rather than unknown at the brace; every release reads 49 characters of a name at most. On random malformed patterns, offsets now agree with PCRE2 in 98.5% of cases, for a PHP 8.4 target and for the running PHP alike.
- More error offsets follow the PCRE2 release that judges the pattern: an alphabetic name PCRE2 10.44 does not know, as `(*scs:`, is refused where the name ends even when a quantifier follows; before 10.45 a character type or a property is refused as a range start on the hyphen and as a range end past its letter (`[\d-a]`, `[z-\p{Lu}]`), a group number past 65535 past the digit that takes it over (`\g66666666`, `(?66666666)`, `(?(8000000000`), and a `(*LIMIT_...)` value past the digit it refuses; before 10.47 `\N{name}` is refused on its brace, a malformed version condition on the character at fault, a verb as a condition on its `*`, and a POSIX item outside a class, as `[:x:]`, on its `[`. `\g{66666666}` and `\g<66666666>` are refused on their brace, as every release does.
- A conditional whose condition is neither an assertion, a number, a version nor a name was accepted: `(?(\1)a)`, `(?(\g{1})a)`, `(?((?=a))b)`, `(?((?1))b)`, `(?({name})a)` and `(?(>name<)a)`, as was a bare name holding other characters, as in `(?(a-b)x)`. PHP refuses each, "subpattern name expected" where the name should start or "missing terminator" where it stops; so does the parser now. The lookaround is written `(?(?=a)b)`, the reference `(?(1)a)` or `(?(<name>)a)`.
- A verb or alphabetic assertion name is read with its digits, as PCRE reads it: `(*MARK9.` and `(*9` are refused where the name ends, not at the digit. From PCRE2 10.47, an alphabetic name followed by no colon, as in `(*pla)` or `(*atomic)`, is refused past the character after it.
- A lookbehind holding an octal escape written `\101`, with fewer groups than its number, was refused as unbounded: `(?<=\101)a` compiles, `\101` being the character `A`. It now counts as one character, and the digits past the three octal ones as literal characters.
- A start-of-pattern setting in the body of an alphabetic assertion, as in `(*pla:(*UTF))` or `(*atomic:(*CR))`, was accepted as if it opened the pattern; PHP refuses it as an unknown verb, and so does the validator now.
- A callout in a condition followed by a comment, an empty `\Q\E` or, under `x`, whitespace before its assertion, as in `(?(?C1)(?#c)(?=a)b)`, was refused; PCRE skips them there as anywhere, and so does the parser now. What comes instead of the assertion is refused where PCRE stops.
- `generate()` lays the text a positive lookahead generates over the text that follows it, and a positive lookbehind's over the text before it, instead of adding them at the ends of the sample: `^(?=.*\d)(?=.*[a-z])\w{8}$` and `a(?=bc)\w\wd` now get a sample that matches. When no attempt matches, text around the sample is tried, which satisfies `\b`, `\Ba\B` or `(?!^)abc`. A relative call, `(?-1)` or `(?+1)`, now counts the groups opened before it; `(?+1)` threw a `LogicException`. On the patterns of the PCRE2 test suite, samples now match for 97% of them, up from 96%.
- `\x` with one hexadecimal digit, as in `\x0` or `\xA`, was parsed with the code point -1, and `\x` with none as the letter `x`, which PCRE2 10.40 to 10.44 read as NUL; both now carry the character they stand for. From PCRE2 10.45, `\x` with no digit stays refused.
- `generate()` left `\g1`, `\g{1}` and the relative `\g-1`, `\g{-1}` references empty, wrote a `\NN` that names no group as nothing instead of the octal character PCRE reads, and wrote a character given by its code as UTF-8 even without UTF mode.
- `generate()` produced an ASCII letter, digit or punctuation mark for any `\p{...}`, which most properties do not hold: `\p{Greek}`, `\p{Zs}` or `\P{L}` gave samples their pattern does not match. It now asks PCRE for characters that have the property. On the PCRE2 test suite, the share of samples that match their pattern went from 69% to 95%.
- The `regex.lint.backref.undefined` rule reported `\11`, `\128` or, in UTF mode, `\666` as references to missing groups; PCRE reads a `\NN` of two digits or more that names no group as an octal escape when it starts with an octal digit, and the rule now leaves those alone.
- An escape such as `\666` or `\6666666666` that names no group and reads as an octal value past `\377` without UTF mode was reported as a reference to a missing group, at the end of its digits; PHP refuses the octal value where its three digits end, and so does the validator now (`regex.octal.out_of_range`).
- A malformed or unclosed `(*LIMIT_MATCH=...)` value, as in `(*LIMIT_MATCH=12bc)`, was reported at the closing parenthesis or at the start of the value; it is now reported where PCRE2 stops reading, which moved by one character in PCRE2 10.45.
- `(*CASELESS_RESTRICT)` and `(*TURKISH_CASING)`, the start-of-pattern settings PCRE2 10.45 added, are accepted when the running PHP links PCRE2 10.45 or later, with the checks PCRE2 makes: Turkish casing needs UTF mode (`regex.verb.turkish_casing_without_utf`) and does not go with the caseless restriction (`regex.verb.conflicting_casings`). For a targeted PHP version they stay unknown verbs, as no PHP bundles 10.45.
- The smallest compiled size the validator proves now counts what classes, callouts, named verbs, properties and the types UCP reads take, as PCRE2 compiles them: `(?:[ab]c){1599}`, `(?:(?C1)a){4681}` or `(?:\p{L}a){5958}/u` were accepted though PHP refuses them as too large. It stays a lower bound: a class PCRE may compile smaller (one member, a case pair, one matching every character) counts as little as it may.
- `[[:<:]]` and `[[:>:]]`, which PCRE2 reads as the start and the end of a word (`\b(?=\w)` and `\b(?<=\w)`), were parsed as a class followed by a literal `]`: the length range, `literals()`, `optimize()` and the explanation all described a different pattern. They now parse into that boundary and lookaround, and compile back as written.
- A version condition with a number over 1000, as in `(?(VERSION=1001.1)...)`, was accepted; PHP refuses it. For PHP 8.2 to 8.5, whose PCRE2 reads a minor of two digits at most, `(?(VERSION>=10.100)...)` was accepted too. Both are now refused where PCRE2 stops reading.
- For PHP 8.2 and 8.3, a lookbehind holding a group of variable length repeated zero times, as in `(?<=a(b?c){0}d)`, was accepted; the PCRE2 those versions bundle does not count it as fixed length, and it is now refused there.
- Group names of 33 to 128 code units were accepted for PHP 8.2 and 8.3, whose PCRE2 stops at 32 (PCRE2 10.44 raised the limit to 128); they are now refused there, where the name ends. A reference or a call to a name past the limit, as in `\k<...>`, `\g{...}`, `(?&...)` or `(?(name)...)`, was reported as a missing group; PHP reports the length, and so does the parser now.
- With a `php_version` target, Unicode property names were judged by the PCRE2 the running PHP links, not the one the targeted PHP bundles: `\p{Kawi}` was accepted for PHP 8.2 and 8.3, `\p{Garay}` and the other Unicode 16 and 17 scripts for every PHP version, as was a `^` after spaces (`\p{ ^Lu}`). They are now refused where the bundled PCRE2 does not know them.
- A pattern ending in `\c\` (the control character 0x1C) followed by an empty `\E` or a space under `x` compiled back with the `\c\` right before the closing delimiter, which PHP then read as escaped: the compiled and optimized forms had no end. The compiler now closes such a run with an empty `\E`.
- A string callout that doubles its delimiter to hold it, as in `(?C"a""b")`, compiled back with the delimiter single, which ended the callout early: PHP refused the result. The text is now written back with its delimiter doubled, and a callout keeps the delimiter it was written with instead of turning into `(?C"...")`.
- `optimize()` dropped a group repeated `{0}` even when it holds a capturing group, which renumbered the groups after it and removed what `(?1)` calls: `(?1)(?:(b)){0}` became `(?1)`, which PHP refuses. It also dropped a possessive `{1}+` as if it were `{1}`, and merged possessive counts into greedy ones, losing their atomicity: `(?:a|ab){1}+c` matches `ac` but not `abc`, its optimized form matched both.
- `literals()` claimed prefixes and suffixes that matches do not have. A lookaround was read as consumed text (`foo(?!bar)` gave the prefix `foobar`); a branch about which nothing was known was left out of a union (`(?:b|:+)` gave the suffix `b`); a set past 100 entries was cut and still reported as the only possibilities; `(*ACCEPT)` was read as an empty string; `(?i)` stopped at its own group, and caseless matching of non-ASCII letters was not folded, nor, in UTF mode, `k` with the Kelvin sign and `s` with the long s. Checked against what PHP matches on the PCRE2 test suite subjects, every match now starts with a reported prefix and ends with a reported suffix. A set too large to keep is now dropped rather than cut.
- The length range counted every literal as one character: an empty group, an empty branch or an option setting such as `(?s)` counted one, a `\Q...\E` run one whatever its length. It now counts what the literal holds (UTF-8 characters in UTF mode, bytes otherwise), `\R` as one or two characters, `\X` as unbounded, and ends at a `(*ACCEPT)`. Lint rules and lookbehind checks that rely on it follow: `(?<=\R)` is now refused for PHP 8.2 and 8.3, whose PCRE2 does not take a lookbehind of variable length.
- `\g{ 1 }`, `\g{ -1 }`, `\k{ name }` and the other braced references padded with spaces or tabs were refused; PCRE2 10.43 accepts them, so PHP 8.4 and 8.5 compile them. They are now read as the reference they pad, and refused for PHP 8.2 and 8.3 where those PHP versions stop reading them.
- `(*atomic_script_run:...)` and `(*asr:...)` were read as opaque verbs: their body was never checked (`(*asr:\y)` and `(*asr:(a)\2)` were accepted), its groups were not numbered (`(*asr:(a))\1` was refused), and the construct could not be repeated. They now parse into a `ScriptRunNode` whose new `atomic` property is `true`, and compile back to the spelling they were written in.
- `(*PLA:...)`, `(*SR:...)`, `(*Atomic:...)` and other spellings of the alphabetic assertions and script runs not in lowercase were accepted; PCRE2 knows them in lowercase only and refuses any other spelling as an unknown verb, and so does the parser now.
- Three limits PCRE sets on what it compiles were not checked, so patterns PHP refuses were reported valid: a `(*MARK)`, `(*PRUNE)`, `(*SKIP)` or `(*THEN)` name longer than 255 code units (`regex.verb.name_too_long`), a `(*LIMIT_MATCH=n)`, `(*LIMIT_HEAP=n)` or `(*LIMIT_DEPTH=n)` value above 4294967289 (`regex.verb.limit_too_large`), and parentheses nested more than 250 deep (`regex.group.nested_too_deep`). Each is reported where PHP reports it.
- For PHP 8.2 and 8.3, `{,2}` and a count padded with spaces (`{ 2 }`, `{2, 3}`) were read as repeats; the PCRE2 those versions bundle reads them as literal text, so `/{,2}/` was refused and `/a{,2}/` misread. They are now text there, and repeats from PHP 8.4. `\N{,2}` is refused before PHP 8.4, and `\N` followed by such a count is reported where the `\N` ends, as PCRE2 10.40 and 10.42 report it.
- The ASCII options PCRE2 10.43 added to `(?...)` — `a` alone, or with one of `D`, `S`, `W`, `P`, `T`, as in `(?aD)` or `(?i-aW:...)` — were refused; PHP 8.4 takes them. They are now read for PHP 8.4 and for a running PHP that links PCRE2 10.43 or newer, and still refused for PHP 8.2 and 8.3.
- Spaces or tabs right after the `U+` of `\N{U+...}` were left unjudged. From PCRE2 10.43 they may only run up to the closing brace (`\N{U+ }`), so `\N{U+ 41}` and an unclosed `\N{U+ ` are now refused; for PHP 8.2 and 8.3, whose PCRE2 refuses any padding there, `\N{U+ }` is refused too.
- An unmatched `)` is reported past the `)` when the running PCRE2 is newer than 10.45, where PHP reports it, and on it for older releases and for an explicit `php_version` target (PHP bundles 10.44); the message now says "Unmatched closing parenthesis".
- A pattern with two errors, one of them a reference to a missing group, was reported at the reference. PCRE resolves references to groups by number or name only once it has read the whole pattern, and measures lookbehinds before that, so `\2\y` fails on the `\y` and `\2x(?<=a+)` on the lookbehind; the validator now reports the same error. Relative references are still judged where they stand, as PCRE does.
- `\c` followed by a tab, a newline, another control character or DEL was reported valid; PCRE takes only printable ASCII after `\c`, and refuses these.
- A malformed `\k` name was reported valid when it had an opener: `\k<`, `\k{ab`, `\k'a`, `\k<a-b>`, `\k{1,}`. PHP refuses them all; they now fail where PCRE stops reading, as `(?<`, `(?&` and `\g` already did.
- Compiling or optimizing a pattern could fuse two items into one longer escape: `(a)\1\E0` compiled to `(a)\10` (the octal `\010`), `\xa\Eb` to `\xab`, `a{\E2}` to the repeat `a{2}`, and optimizing `(a)\1(?:)0` gave `(a)\10`. A `\E` or `\Q\E` is still dropped where it separates nothing, and kept as written where dropping it would join two items; where no source says how two items were separated, an empty group (`\E` in a class) keeps a digit escape apart from the next digit.
- `\p` and `\P` with no property after them (`\p`, `\p1`, `\p\E{L}`, an unclosed `\p{L`, the empty `\p{}`) were read as the letters `p` and `P` and reported valid; PHP refuses them. They now fail with `regex.unicode.property_malformed` (or `regex.unicode.property_invalid` for `\p{}`) at PCRE's offset.
- Compiling a pattern that opens with `(*UTF)` but has no `u` flag wrote its non-ASCII characters back as separate bytes (`é` as `\xC3\xA9`), which UTF mode reads as two characters; they are now kept whole, as under `u`.
- A `\Q` run left open at the end of the pattern kept its final newline out of the tree, so recompiling `/a\Q\n/` dropped the newline and matched `a` alone.
- Errors are reported at the offset PHP reports: `ValidationResult::$offset`, and the position an error message quotes, now point at the byte of the pattern body where `preg_match()` places its "Compilation failed: ... at offset N" warning, which is usually where PCRE stops reading the construct at fault. `\1` with no group is reported at 2, the end of the reference, not at 0; `[a-\d]` at 5, after the class escape; `(?<=x(a+))` at 0, the start of the lookbehind, rather than at the `+`; `(?z)` at 3, past the unknown letter; `(?<0a>x)` at 4, past the leading digit; a duplicate group name past the `>` that closes it. Where PHP releases disagree on an offset, the library reports the one of PCRE2 10.48 or, for a construct only newer releases read such as `(?[...])`, the one of the PCRE2 10.40 that PHP 8.2 bundles. Whether a pattern is valid is unchanged, and body offsets stay relative to the pattern body. A pattern holding two errors may now report the other one, the one PHP reports: `[\d-\N]` the `\N` a class refuses rather than the range, `x{70000,1}` the number too big rather than the reversed bounds.
- A `(?#...)` comment between an item and its quantifier no longer takes the quantifier: PCRE skips the comment, so `a(?#c)*` repeats the `a`, and `a*(?#c)+` is the possessive `a*+`. The tree used to repeat the comment and match a single `a`, so generated samples, ReDoS and lint results followed the wrong pattern. With nothing repeatable before the comment, as in `(?#c)*`, `(?i)(?#c)*` or `^(?#c)*`, validation now refuses the quantifier at the offset PHP reports, as `preg_match()` does; it used to accept it. Recompiling puts the comment after the quantifier: `a(?#c)*` comes back as `a*(?#c)`.
- A quantifier after a `\Q...\E` run repeats the run's last character only, as in PCRE: `\Qab\E*` is `ab*` and `\Qab\E{2}` is `abb`. The tree repeated the whole run, so a generated sample such as `abab` was one the pattern does not match. The last character is a code point in UTF-8 mode and a byte otherwise. A lone `\E` or an empty `\Q\E` is skipped like a comment: `a*\E+` is the possessive `a*+`, `/^a\E {,2}$/x`, which was refused, validates, and `a{1,3}\E{2}` and `a*\Q\E*` are refused at the offset PHP reports; they validated.
- Inside a class, a `\Q...\E` run stands for its characters one by one, as in PCRE: `[\Qabc\E-z]` is `a`, `b` and the range `c-z`, and `[\Qaz\E-a]` is refused as the reversed range `z-a`.
- An `\E`, or an empty `\Q\E`, between a range start and its hyphen no longer breaks the range: PCRE builds it through them, so `[a\E-c]` matches `b`, and `[z\E-a]` is refused as a reversed range, as `preg_match()` refuses it. After a class escape, `[\w\E-a]`, the hyphen stays a member up to PCRE2 10.44, the newest any PHP release bundles; only a newer linked PCRE2, without an explicit `php_version`, refuses it.
- `[a&&b]` and `[a--b]` read as PCRE reads them. PHP compiles without PCRE2's extended class syntax, so `&&` and `--` inside a class are not an intersection and a subtraction: `[a&&b]` holds `a`, `&` and `b`, and `[a--b]` is a range from `a` down to `-`, which PHP refuses. Validation accepted `[a--b]`, `[a--]`, `[^^--]` and `[\w--\d]`, and refused `[--[]` and `[]-\E]`; a `[` after `&&` opened a nested class, so `[a-z&&[^aeiou]]` was read as one class where PHP reads a class followed by a literal `]`.
- Spaces inside `\x{ 41 }`, `\o{ 101 }`, `\N{ U+41 }` and a `\N{4 }` repeat arrived in PCRE2 10.43, which PHP bundles from 8.4; they validated for any target. Targeting PHP 8.2 or 8.3, they are now refused, as those releases' PCRE2 refuses them, unless the running PHP links a newer PCRE2. The unpadded forms are valid everywhere, and `a{ 4 }` is unchanged.
- Under the `n` modifier or `(?n)`, a plain `(...)` group was counted as a capture, so `/(?n)(a)\1/` and `/(a)\1/n` validated though PHP refuses them. Such a group now captures nothing and takes no number — named groups still do — through `(?n:...)`, `(?-n)` and `(?^)` as PCRE scopes them. It is read as a non-capturing group and written back with the `(` it was spelled with.
- `\g'1'` and `\g'-1'` call the group, as `\g<1>` does; they were read as back references.
- A pattern cut short by an unescaped delimiter is reported as such, at that delimiter: `/a/b/` gives "Unescaped delimiter \"/\" at position 2 ends the pattern early" rather than a list of unknown modifiers, or a misleading note about the removed `e` modifier when the cut-off text holds an `e`.
- `\g{name}` was read as a call to the group, and written back as `\g<name>`, which changes what the pattern matches: `/(?<n>a|b)\g{n}/` refuses "ab", but its rewrite matched it. It is now a back reference, like `\k{name}`, and is written back as `\g{name}`. `\g<name>` and `\g'name'` stay calls.
- A delimiter inside a character class, a comment or a `\Q...\E` run no longer hides from the end of the pattern: PHP ends a pattern at the first delimiter a backslash does not escape, so `/[/]/` has the unknown modifiers `]/` and is refused, as `preg_match()` refuses it. Such patterns, like `"/([[:alnum:]]+)://.../i"`, fail at runtime with a warning and a `null` result; validation used to report them as valid.
- Validation accepted variable-length lookbehinds such as `(?<=a?)b` when targeting PHP 8.2 or 8.3, whose bundled PCRE2 (10.40, 10.42) refuses them: they need PCRE2 10.43, bundled from PHP 8.4 (`regex.lookbehind.variable_length_not_supported`). Branches of different fixed lengths, `(?<=a|bc)b`, stay valid everywhere. Without an explicit `php_version`, the PCRE2 the running PHP links decides, and one from 10.45 on also refuses a `\x` with no digit.
- Validation refused `\K` inside a lookbehind (`regex.lookbehind.keep_not_allowed`), though PHP compiles it: PHP enables `PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK` by default, and PCRE2 allowed it there before 10.38. `/(?<=a\K)b/` validates now.
- Installing `nikic/php-parser` changed what `regex lint` reported: the AST extractor missed the patterns held in an array — `preg_replace(['/a/', '/b/'], ...)` and every `preg_replace_callback_array()` key — that the tokenizer already read. Both extractors now recognise the same calls, and the AST one also reads a pattern passed as a named argument.
- Without `nikic/php-parser`, `regex lint` missed patterns the AST extractor read: a nowdoc or a heredoc without interpolation, a pattern passed by name (`preg_match(subject: $s, pattern: '/a/')`), and the string form of a call whose array form holds patterns in its keys (`Strings::replace($s, '/a/', 'b')`). The tokenizer reads them too, a heredoc decoded as PHP decodes it.
- Without `nikic/php-parser`, `regex lint` placed a pattern a few characters off (the column of the console, GitHub and Checkstyle reports, `column` and `file_offset` in JSON) when an argument read before it held braces: a closure body, `"{$x}"`. A binary string, `b'/a/'`, kept its `b'` in the pattern; it is read as PHP reads it.
- With the `nette-utils` preset, `Strings::replace()` is read as Nette reads it: the keys of an array of patterns only when its first key is a string and the replacement is no callable, the values otherwise (a list, or a closure, an arrow function, a first-class callable, an array, an object, `$this`, an `(object)` or `(array)` cast, a `clone` or `Closure::fromCallable()` as replacement; a key that is an int, a float, `true` or `false`, in parentheses or signed, makes a list). Both extractors read the keys of every array.

- From PCRE2 10.47 an alphabetic name followed by no colon is refused past the whole character after it in UTF mode, as PCRE2 does: `/(*aé)/u` at offset 5 and `/x(*a名)y/u` at offset 7, where the library stepped one byte past the name, 4 and 5.
- A verb no `)` closes has its name read as in a closed one: a name longer than a group name may be is refused as one too long, `regex.group.name_too_long`, where it ends (`(*ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghij` at offset 38 up to PCRE2 10.43, a name past 128 characters from 10.44), where the library said `regex.verb.unclosed` or `regex.verb.invalid`; on 10.32 the name is a run of letters, refused on a digit that opens it (`(*1a`: offset 2, `regex.group.name_invalid`), at the 33rd letter, and where the letters end (`(*UTF8`: offset 5), where the library read digits and underscores in it.
- A script run name closed with no colon, as `(*sr)`, `(*asr)`, `(*script_run)` or `(*atomic_script_run)`, is refused as an alphabetic name PCRE2 does not know (`(*sr)`: offset 4, 5 from PCRE2 10.47), on every release from 10.33 and on 10.32 where its letters end; the library compiled it.
- From PCRE2 10.47 an alphabetic name closed with no colon that ends a pattern leaving a group open, as `(?:(*m)` or `(?:(*pla)`, is refused as that name, `regex.verb.invalid`, as PCRE2 refuses it before it finds the group open; the library said `regex.group.unclosed` at the same offset.
- After a callout, the condition of `(?(` wants an assertion whatever PCRE2 reads as nothing before it, a comment, `\E`, `\Q\E` or under `x` white space and a line comment: a verb there is refused on its `(` (`(?(?C1)(?#c)(*UCP:x)|b)`: offset 17, `(?(?C1)(*ABCDEFGHIJKLMNOPQRSTUVWXYZABCDEFGH)a)` up to PCRE2 10.43: offset 7), and on 10.32 an alphabetic name too (`(?(?C1)(*pla:a)b)`: offset 7), where the library refused the name; an alphabetic name of more than 32 characters there, never closed, is refused as one too long up to 10.43, and from 10.47 past the whole character after the name in UTF mode; an unknown alphabetic name with a colon where a group name is due, as `(?<(*abc:x`, is refused as no name on its `(`, offset 3, where the library refused the name where it ends.
- A lookbehind is measured as PCRE2 ends its measure. Up to PCRE2 10.42 a repeat of variable count has no fixed length whatever it repeats, an empty group, an assertion or a repeated `(*ACCEPT)` included (`(?<=(?:)?)`, `(?<=()?)`, `(?<=(?:){1,2})`, `(?<=(?<=a)?)`, from 10.34 `(?<=(*ACCEPT)?)`: offset 0, `regex.lookbehind.variable_length_not_supported`), where the library compiled them; and the measure ends at the first item of no fixed length, so a lookbehind after it is never measured (`(?<=xa?(?<=b+))` is refused at 0, not at the inner lookbehind). On every release `(*ACCEPT)` and `(*FAIL)` end the branch they stand in, so what follows them there is not measured (`(?<=a(*ACCEPT)b+)` and `(?<=a(*ACCEPT)(?<=b+))` compile), a condition with no `|` is measured as its one branch (`(a)(?<=(?(1)b))` compiles up to 10.42, `(a)(?<=(?(1)b{256}))` from 10.43), and a lookbehind in a DEFINE group inside a lookbehind is never measured from PCRE2 10.35 (`(?<=(?(DEFINE)(?<=b+))c)` compiles); the library refused them. A branch of one length past 65535 is refused as too long before a later branch of no fixed length or no bound (`(?<=a{65535}a{2}|b+)`: `regex.lookbehind.too_long`, where the library said unbounded), and each branch of a condition counts toward the 2,001 branches PCRE measures (`(?<=(?(1)a|b)…)` repeated 1,001 times is `regex.lookbehind.too_complex`, where the library compiled it).
- The body of a `(*scs:` or `(*scan_substring:` that no `)` closes is read after its list of groups, as PCRE2 reads it: the first error in it is reported where it stands (`(*scs:(1)(*UTF:x)`: offset 14, `regex.verb.invalid`; `(*scs:(1)[a`: offset 11, `regex.charclass.unclosed`; `(*scs:(1)(*pla)`: offset 14, 15 from PCRE2 10.47), where the library reported the `)` missing at the end of the pattern; a group zero, a relative zero or a relative group before the first in its list is refused there before the body (`(a)(*scs:(+0)\c`: offset 12, `regex.group_list.relative_zero`).
- Property escapes are refused where each release refuses them: under UTF, `\pé` or `[\pé]` is malformed one byte into the character up to PCRE2 10.46 (`\pé`: offset 3, 4 from 10.47); a name past 49 code units counts bytes up to 10.46; up to 10.44 a `^` after a space, hyphen or underscore is a letter of the name, so `\p{-^LL-}` and `\p{_^Lu}` are unknown properties, and from 10.45 the name after it is looked up, so `\p{ ^Foo}` and `\P{ ^}` are refused on 10.45 to 10.48 and a script of Unicode 17 there needs 10.48, where the library compiled them; a second `^` in a name is refused as no name holds it (`\P{^ ^L}`: offset 7, where the library compiled it), and `\P{_^L}` compiles from 10.45 on the running engine too. A range from a class escape in the body of an alphabetic assertion is refused before a `\c` PCRE refuses later in the class (`(*pla:[\d-a\cé])`: offset 9, 10 from 10.45), as in a lookahead; and for PHP 7.3 and 7.4 without `X`, a `\p{` no `}` closes, read as `p{`, no longer hides an error after it (`\P{[z-a])`: offset 6; `[^a[-\P{]a)` on PHP 7.3: offset 6).
- Literal extraction no longer walks a count repetition by repetition once the sets it builds come back: `Regex::literals('/a{99999999}/')` took past two minutes and now takes milliseconds, `/[ab]{65535}/` 9 ms instead of 270 ms, with the same literals for every pattern. The test case generator builds no case for a pattern the running engine refuses, which it kept none of: `(?:a{60000}){60000}` ran out of memory building cases of 3.6 GB.
- With the PCRE2 that PHP 8.2 to 8.4 bundle, 10.40 to 10.44, and its JIT on, as in the official arm64 Docker images, the parser read every `(` of a pattern, and every lookbehind it reported as too complicated, in time growing with the rest of the pattern: it looked for the `:` of `(*name:` with a regex, and such a regex has PCRE2 search the whole rest of the subject for the `:` it must end with. 64,000 groups took 2.3 s to tokenize, 60,000 unclosed `(*` 1.4 s; they now take 0.35 s and 0.22 s, and the time grows with the pattern on every release, with the JIT or without it.
- The body of an alphabetic assertion or a script run, `(*pla:…)` or `(?*…)`, is read without searching the options a pattern opens with for their `)` again for each body, nor copying the body more than once: after a first body holding a 200 KB line comment, 4,000 bodies took 1.2 s to parse with PCRE2 10.44, ten times as long as 1,000, and now take 0.06 s; 1,000 nested `(*atomic:` bodies take 0.02 s, where they took 0.05 s.
- In a pattern refused further on, a run of version conditions that no `)` closes is judged in linear time: 2,000 `(?(VERSION` took 0.9 s to validate, 9,600 took 24 s; 2,000 now take 0.05 s.
- `validate()` and `parse()` no longer loop for ever on a setting written after `\E` and a comment at the start of a pattern that ends with it, `/\E(?#c)(*UTF)/`: the walk back over what PCRE reads as nothing read the last character of the pattern for the one before its first. It is now refused where PCRE refuses it, `regex.verb.misplaced` at 12.
